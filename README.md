# VS Code as a Galaxy Interactive Tool

Visual Studio Code (OpenVSCode Server) packaged as a Galaxy Interactive Tool.
It installs on any Galaxy that can run interactive tools and supports both of
Galaxy's layouts:

- **Path based**: `https://<galaxy host>/<prefix>/interactivetool/ep/<id>/<token>/`.
  No DNS or certificate work, and the only layout that works behind a shared
  proxy. This is the default.
- **Domain based**: `https://<id>-<token>.ep.interactivetool.<galaxy host>/`.
  Needs a wildcard DNS record and a wildcard certificate for
  `*.ep.interactivetool.<galaxy host>`.

The same image serves both.

## Requirements

- Galaxy 23.0 or later with interactive tools enabled.
- A job destination that can expose a container port: the Kubernetes runner, or
  a Docker-enabled local, Slurm or Pulsar destination. Cloud batch runners such
  as GCP Batch cannot run interactive tools.
- Galaxy served over HTTPS. The editor works over plain HTTP, but Markdown
  preview and other webviews need a secure context and stay blank without one.
- Users must be logged in: the tool gives each session the launching user's
  API key.

## What is in this repository

| Path | What it is |
|---|---|
| `tool/` | The tool: `interactivetool_vscode.xml` and `macros.xml`, which holds every setting |
| `install.sh` | Copies `tool/` into a Galaxy tool directory with the mode and image set |
| `config/galaxy.yml` | The `interactivetools_*` settings for each mode |
| `config/job_conf.yml` | Docker and Kubernetes destinations that can run interactive tools |
| `config/tpv_rules.yml` | The same routing for Total Perspective Vortex |
| `config/nginx.conf` | nginx fragments for both modes |
| `config/tool_conf.xml` | Toolbox file that adds the tool to an "Interactive Tools" section |
| `helm/vscode-it.yml` | Values overlay for galaxy-helm, generated by `scripts/render_helm.py` |
| `docker/` | The container image |

The files under `config/` are references to merge into your own configuration.
Nothing installs them for you.

## Installing on a Galaxy server

### 1. Install the tool

    ./install.sh --mode path   --tool-path /srv/galaxy/server/tools
    ./install.sh --mode domain --tool-path /srv/galaxy/server/tools

`--tool-path` is Galaxy's `tool_path`, usually `<galaxy root>/tools`. The
installer writes `<tool-path>/interactive/vscode/` and prints the remaining
steps. Add `--container IMAGE` to use an image other than the default
`ksuderman/galaxy-vscode:1.105.1-5`.

To install by hand, copy `tool/` to that directory and edit the tokens in
`macros.xml`:

| Token | Meaning |
|---|---|
| `@CONTAINER@` | The image to run |
| `@REQUIRES_DOMAIN@` | `False` for path based, `True` for domain based |
| `@TOOL_VERSION@` | The tool version shown in Galaxy |

### 2. Add it to the toolbox

Add `config/tool_conf.xml` to `tool_config_file`, or add its one line to a tool
conf you already load:

    <tool file="interactive/vscode/interactivetool_vscode.xml" />

### 3. Configure galaxy.yml

Merge the keys from `config/galaxy.yml`. The comments in that file say which
values belong to which mode. In short:

- `interactivetools_enable: true`
- `interactivetools_map` on storage that every Galaxy handler can see.
  Otherwise stopping a session fails with "no such table: gxitproxy".
- Path mode behind nginx: `interactivetools_upstream_proxy: true` and leave
  `interactivetools_proxy_host` unset.
- Domain mode: `interactivetools_proxy_host: <galaxy host>`.

### 4. Route the tool to a destination that can expose a port

`config/job_conf.yml` has a Docker destination and a Kubernetes destination
with the settings a WebSocket-heavy IDE needs. `config/tpv_rules.yml` is the
TPV equivalent. If you also have destinations that cannot run interactive
tools, pin `interactive_tool_.*` to one that can.

### 5. Configure the proxy

Run gx-it-proxy (the galaxyproject.galaxy Ansible role starts it through
Gravity; see the end of `config/galaxy.yml`) and add the fragment for your mode
from `config/nginx.conf`.

Domain mode also needs the wildcard DNS record `*.ep.interactivetool.<galaxy
host>` and a certificate that covers it. Let's Encrypt issues wildcard
certificates only through the DNS-01 challenge.

### 6. Restart Galaxy

Tool definitions are read at startup. "VS Code" then appears in the tool panel
under "Interactive Tools".

## Installing on Kubernetes with galaxy-helm

`helm/vscode-it.yml` is a values overlay that does all of the above: it embeds
the tool, adds it to the toolbox, enables interactive tools, configures the
Kubernetes runner and routes interactive tools to it.

    helm upgrade --install galaxy <chart> -f values.yml -f helm/vscode-it.yml

The Kubernetes runner creates a Service and an Ingress for every session, so no
gx-it-proxy is involved.

The committed overlay is path based. Two settings may need changing for your
cluster:

- `interactivetools_proxy_host` is empty, which suits a Galaxy Ingress with no
  host. If Galaxy's own Ingress names a host, set this to the same host, or the
  session Ingress never matches a request.
- The overlay requires a destination tagged `interactive`. Add that tag to the
  Kubernetes destination in your TPV configuration.

For domain mode, render the overlay again and apply the result:

    scripts/render_helm.py --mode domain --output vscode-it-domain.yml

Then set `interactivetools_proxy_host` to the Galaxy hostname, set
`k8s_interactivetools_use_ssl: true`, name the wildcard certificate's Secret in
`k8s_interactivetools_tls_secret`, and point the wildcard DNS record at the
ingress controller.

If the tool is installed from a ToolShed instead of being embedded, render the
configuration alone and use that file in place of the overlay:

    scripts/render_helm.py --no-tool --output vscode-it-config.yml

After changing the overlay on a running deployment, restart the web, job and
workflow deployments. Mounted tool files are not picked up live.

## Using it

Run "VS Code" from the tool panel, optionally selecting datasets from the
current history. When the job starts, open the session from the link Galaxy
shows or from User > Active Interactive Tools.

### Files

- `inputs/` holds the datasets selected at launch, linked read-only.
- `outputs/` is collected when the session stops. Every file saved there with a
  file extension, such as `notes.txt` or `result.tsv`, is imported into the
  history as a collection.

Everything else is discarded when the session stops, including the rest of the
workspace, editor settings, installed extensions and conda environments.

### Moving data during a session

The integrated terminal has `GALAXY_URL`, `API_KEY` and `HISTORY_ID` set, and
two helpers that use them:

    galaxy-get <dataset> [destination]    # copy a dataset from the history
    galaxy-put <file> [<file> ...]        # upload files to the history now

`<dataset>` is a history item number (the "3" in "3: my.fasta"), a dataset id
or an exact dataset name. `bioblend` is installed for anything else.

### Software

- `python3` with `bioblend` and `ipykernel`. Notebooks (`.ipynb`) run with the
  pre-installed Jupyter extension; select `/usr/bin/python3` as the kernel.
  `numpy`, `pandas`, `scipy`, `scikit-learn`, `matplotlib` and `seaborn` are
  installed for it.
- R with `languageserver`, `IRkernel` (the "R" notebook kernel) and `httpgd`
  for plots.
- `micromamba` for conda-forge and bioconda packages:

      micromamba create -n work -c conda-forge -c bioconda samtools
      micromamba activate work

- `conda-pack`, to archive a conda environment for a later session (see
  below).
- `git`, `git-lfs`, `curl`, `jq`, `nano`, `unzip`.
- `gcloud` and `gsutil`. On a Google Cloud VM they authenticate as the VM's
  service account with no login.
- The Python, Jupyter and R extensions. More can be installed from the
  Extensions view, which uses the Open VSX registry.

The image has no compilers, so `BiocManager::install()` fails for packages that
need compiling. Install Bioconductor packages prebuilt from bioconda instead:

    micromamba create -n bioc -c conda-forge -c bioconda r-base=4.5 bioconductor-limma r-irkernel
    micromamba run -n bioc Rscript -e 'IRkernel::installspec(name="bioc", displayname="R (bioc)")'

The second command makes that environment's R available as a notebook kernel.

### Keeping a conda environment between sessions

Conda environments are discarded with the session, and copying one back by
hand does not work, because an environment records the directory it was built
in and that directory is different in every session. `conda-pack` produces an
archive that can be restored anywhere.

Save an environment, here to a Google Cloud Storage bucket the session can
write to, such as the workspace bucket on Terra:

    conda-pack -p ~/micromamba/envs/work -o work.tar.gz
    gcloud storage cp work.tar.gz gs://<bucket>/galaxy-vscode/work.tar.gz

Restore it in a later session:

    gcloud storage cp gs://<bucket>/galaxy-vscode/work.tar.gz .
    mkdir -p ~/micromamba/envs/work
    tar -xzf work.tar.gz -C ~/micromamba/envs/work
    python3 ~/micromamba/envs/work/bin/conda-unpack
    micromamba activate work

Run `conda-unpack` with `python3` as shown. It repairs the paths inside the
environment, and calling it directly fails in an environment that has no
Python of its own.

Without a bucket, keep the archive in the history instead: `galaxy-put
work.tar.gz` to save it and `galaxy-get work.tar.gz` to fetch it back.

Archives of large environments, R and Bioconductor ones in particular, can be
a gigabyte or more.

### Run an analysis here, or send it to Batch

Your terminal, scripts and notebook kernels run inside the IT container and
share its CPU and memory. The supplied configuration requests **1 CPU and
4 GB RAM**, although your Galaxy deployment may provide different resources.
Keep small analyses here; for larger work, you can send a job to Google Cloud
Batch and continue editing while it runs on a separate VM.

The examples below take a table from your Galaxy history, process it on Batch,
and bring the result back. Batch compute is billed separately. You will need a
Google Cloud project with Batch enabled, a job service account you can use, and
a bucket accessible to both your terminal identity and that service account.
Check the current identity and project with `gcloud auth list` and
`gcloud config get-value project`.

#### Example 1: summarize a table on Batch

Choose a table with gene IDs in the first column and numeric gene lengths in
the second. Replace `gene-length.tabular` with its name or number in your history,
and fill in your bucket name and job service-account email:

```bash
galaxy-get gene-length.tabular input.tsv
BUCKET=YOUR_BUCKET
SERVICE_ACCOUNT=YOUR_JOB_SERVICE_ACCOUNT
REGION=us-east4
JOB=vscode-$(date +%s)
STAGING="gs://$BUCKET/$JOB"
```

Save this short script as `analyze.R`:

```r
x <- read.delim("/data/input.tsv")
result <- data.frame(genes = nrow(x), mean_length = mean(x[[2]]))
write.table(result, "/data/result.tsv", sep = "\t", row.names = FALSE)
```

Batch cannot see files in the IT directly. Copy the input and script to your
bucket; the job below mounts that folder at `/data` in its R container:

```bash
gcloud storage cp input.tsv analyze.R "$STAGING/"
cat > job.json <<EOF
{
  "taskGroups": [{"taskCount": 1, "taskSpec": {
    "runnables": [{"container": {
      "imageUri": "bioconductor/bioconductor_docker:RELEASE_3_22",
      "entrypoint": "Rscript", "commands": ["/data/analyze.R"],
      "volumes": ["/mnt/data:/data"]
    }}],
    "computeResource": {"cpuMilli": 1000, "memoryMib": 1024},
    "maxRunDuration": "900s", "maxRetryCount": 0,
    "volumes": [{"gcs": {"remotePath": "$BUCKET/$JOB"}, "mountPath": "/mnt/data"}]
  }}],
  "allocationPolicy": {
    "instances": [{"policy": {"machineType": "e2-standard-2"}}],
    "serviceAccount": {"email": "$SERVICE_ACCOUNT"},
    "location": {"allowedLocations": ["regions/$REGION"]}
  },
  "logsPolicy": {"destination": "CLOUD_LOGGING"}
}
EOF
gcloud batch jobs submit "$JOB" --location="$REGION" --config=job.json
gcloud batch jobs describe "$JOB" --location="$REGION" --format='value(status.state)'
```

Run the last command again to check progress. When it reports `SUCCEEDED`, your
result is in the bucket. Download it into the IT and add it to your history:

```bash
gcloud storage cp "$STAGING/result.tsv" outputs/result.tsv
galaxy-put outputs/result.tsv
```

#### Example 2: use two Bioconductor workers

Reuse the staged input, but replace `analyze.R` with this version. It splits the
gene lengths into two chunks and summarizes them with `BiocParallel`:

```r
if (!requireNamespace("BiocParallel", quietly = TRUE))
    BiocManager::install("BiocParallel", ask = FALSE, update = FALSE)
library(BiocParallel)
x <- read.delim("/data/input.tsv")
chunks <- split(x[[2]], rep(1:2, length.out = nrow(x)))
result <- bplapply(chunks, function(z) c(genes = length(z), mean_length = mean(z)),
                  BPPARAM = MulticoreParam(workers = 2))
write.table(do.call(rbind, result), "/data/result-parallel.tsv",
            sep = "\t", col.names = NA)
```

In `job.json`, change `cpuMilli` to `2000` (two CPUs) and `memoryMib` to `4096`
(4 GiB). Upload the revised script and submit with a new job name, keeping the
same staging folder:

```bash
gcloud storage cp analyze.R "$STAGING/"
JOB=vscode-parallel-$(date +%s)
gcloud batch jobs submit "$JOB" --location="$REGION" --config=job.json
gcloud batch jobs describe "$JOB" --location="$REGION" --format='value(status.state)'
# Once SUCCEEDED:
gcloud storage cp "$STAGING/result-parallel.tsv" outputs/result-parallel.tsv
galaxy-put outputs/result-parallel.tsv
```

More CPUs help when your code uses parallel workers or threads. This small
example shows the setup; parallel overhead may outweigh any speedup for a small
table. For random workloads, pin the generator and seed for reproducible results.
Batch uses the chosen container's software, so packages installed in the IT are
not carried over.

Files written under `/data` stay in the bucket. Other worker-local files do not
automatically return to the IT; logs go to Cloud Logging. Keep the bucket copies
you need and remove temporary inputs and results when finished.


### Stopping

Stop the session from User > Active Interactive Tools. Galaxy ends the job and
imports the contents of `outputs/`.

## Building your own image

Only needed to change what is installed. The image is
`gitpod/openvscode-server` plus the software listed above.

    cd docker
    REGISTRY=<your registry> TAG=<tag> ./build.sh
    docker push <your registry>/galaxy-vscode:<tag>
    ../scripts/dev/test_image.sh <your registry>/galaxy-vscode:<tag>

`IMAGE_NAME` and `OPENVSCODE_VERSION` can be overridden the same way. Use a new
tag for every build instead of moving an existing one: nodes that already
pulled a tag will not see it change. Then pass the image to `install.sh
--container`, or set `@CONTAINER@` in `tool/macros.xml` and run
`scripts/render_helm.py` to regenerate the Helm overlay.

`test_image.sh` runs the image the way Galaxy's Docker runner does and checks
both modes. To try the image by hand:

    docker run --rm -e EP_PATH=/galaxy/interactivetool/ep/1/t -w /jobdir -v $PWD:/jobdir \
        --user 10001:10001 -p 3000:3000 ksuderman/galaxy-vscode:1.105.1-5
    # open http://localhost:3000/galaxy/interactivetool/ep/1/t/
    # domain mode: -e EP_PATH=/ and open http://localhost:3000/

Keep the image without an `ENTRYPOINT`. Galaxy's Docker runner passes the tool
script as the container command, and an entrypoint would swallow it.
